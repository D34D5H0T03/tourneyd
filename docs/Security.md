# Security Notes

**Applies to:** tourneyd `v1.0` (fork concurrency model)
**Last updated:** 2026-10-26

This document records what the server defends against, how each defense works, where it lives in the code, how it was verified, and what is deliberately **not** covered yet. Update it whenever a limit, a defense, or a test changes.

---

## 1. Scope and threat model

**In scope:** untrusted HTTP/1.0 and HTTP/1.1 clients, connecting directly or through a Cloudflare quick tunnel, sending arbitrary bytes at the parser, router, static file handler, JSON API, database layer, response builder, logger and connection management. Also in scope: the content-authoring tool (`tourneyctl`) and the seed script, because they handle flags.

**Current attack surface:**

| Surface | What is exposed |
|---|---|
| Static files | `GET` and `HEAD` for everything under the document root, including generated challenge attachments in `public/files/` |
| Read API | `GET /api/challenges`, `GET /api/challenges/<slug>`, `GET /api/writeups`, `GET /api/writeups/<slug>` |
| Write API | `POST /api/challenges/<slug>/submit` (checks a flag, appends one row to the attempt log) |
| Not exposed | No accounts, no sessions, no cookies, no endpoint that creates or changes challenges or writeups (that is done offline with `tourneyctl`) |

**Out of scope for v1.0:**

| Area | Status |
|---|---|
| TLS | Not implemented. Cloudflare terminates TLS for tunnel deployments. Own TLS is planned (OpenSSL). |
| Volumetric / network-layer DoS | Not addressed by the server. The tunnel provider absorbs most of it. |
| Authentication, sessions, CSRF | Not built. There are no cookies, so there is nothing for CSRF to abuse yet. |
| Per-user abuse controls | There are no users. Rate limiting is per challenge, not per person. |

**Trust boundaries:**

- Every byte read from a socket is untrusted, and so is every value read back from the database for display (the frontend escapes it).
- The configuration file, command-line flags, the `migrations/` directory and everything passed to `tourneyctl` are trusted (written by the operator).
- The `CF-Connecting-IP` header is trusted **only** when `trust_proxy` is on, the TCP peer is loopback, and the value parses as an IP address.

## 2. Defenses at a glance

| # | Threat | Defense | Where |
|---|---|---|---|
| 1 | Direct exposure to the network | Binds `127.0.0.1` by default. The tunnel is outbound-only, so no inbound port or firewall change is needed. | `net/listener.c`, `core/config.c` |
| 2 | Buffer overflows while parsing | Fixed-size fields, every length checked before any copy, explicit-length operations on network data | `http/parser.c` |
| 3 | Oversized requests | Hard limits on line, header, path, query and body sizes (section 3) | `http/parser.c`, `core/config.c` |
| 4 | Request smuggling | See section 4.1 | `http/parser.c` |
| 5 | Path traversal | See section 4.2 | `app/static_files.c`, `http/url.c` |
| 6 | Response splitting / header injection | CR and LF rejected in header names and values; framing headers are reserved and generated by the serializer | `http/response.c` |
| 7 | Content sniffing, XSS, clickjacking | Default security headers on every response (section 4.3) | `http/response.c`, `connections/http_connection.c` |
| 8 | Log injection and forgery | Control characters stripped by the logger; logged fields cleaned and length-bounded; forwarded client IP validated | `util/log.c`, `connections/http_connection.c` |
| 9 | Slowloris and idle-connection hoarding | Absolute per-phase deadlines (idle vs request) on a monotonic clock | `net/conn.c`, `connections/http_connection.c` |
| 10 | Connection floods | Cap on concurrent children; the parent stops calling `accept()` at the cap | `concurrency/fork_model.c` |
| 11 | Runaway or leaking children | Per-child resource limits (memory, CPU, file descriptors) | `concurrency/fork_model.c` |
| 12 | Descriptor and zombie leaks | Parent closes the client fd after `fork()`, child closes the listener, `SIGCHLD` reaping, `SOCK_CLOEXEC` | `concurrency/fork_model.c`, `net/conn.c` |
| 13 | Unclean shutdown | Flag-only signal handlers, drain with a grace period, `SIGKILL` for stragglers | `core/signals.c`, `concurrency/*.c` |
| 14 | Silent child crashes | Children killed by a signal are reported in the error log | `concurrency/fork_model.c` |
| 15 | Process death on write to a closed socket | `SIGPIPE` ignored and `MSG_NOSIGNAL` on every send | `core/signals.c`, `net/conn.c` |
| 16 | SQL injection | Prepared statements with bound parameters only; slugs validated before any query; schema `CHECK` constraints as a second layer | `db/models/*.c`, `app/api_util.c`, `migrations/` |
| 17 | Flag disclosure from the database | Only a per-challenge salt and `SHA-256(salt \|\| flag)` are stored; constant-time comparison | `util/hash.c`, `db/models/challenge_model.c` |
| 18 | Flag disclosure through the API | No response struct has a field for the hash or salt; submitted flags are never echoed or logged | `db/models/`, `app/challenges_api.c`, `connections/http_connection.c` |
| 19 | Flag guessing | Per-challenge limit of 30 attempts per minute, kept in the database (shared across children), answered with `429` and `Retry-After` | `db/models/challenge_model.c`, `app/challenges_api.c` |
| 20 | Database file exposure | Created with mode `0600` in a `0700` directory, outside the document root | `db/db.c` |
| 21 | Malformed or malicious stored text | The CLI validates UTF-8 and sizes; the JSON writer escapes control characters and replaces invalid UTF-8; the schema bounds sizes in bytes | `tools/tourneyctl.c`, `util/json.c`, `migrations/001_init.sql` |
| 22 | XSS in the frontend | CSP forbids inline code; all server text is inserted with `textContent`; no HTML-string sinks in the JS (checked by a test) | `public/js/*`, `http/response.c` |
| 23 | Malicious links in content | Only `http(s)` source URLs are accepted by the CLI and rendered by the page; attachment links must match a strict `/files/<slug>/<file>` pattern | `tools/tourneyctl.c`, `public/js/common.js` |
| 24 | Cross-origin reads of the API | No CORS headers are sent, so other origins cannot read responses | `app/api_util.c` |

### Status codes returned for rejected input

| Status | Meaning in this server |
|---|---|
| 400 | Malformed request, forbidden characters, conflicting or invalid `Content-Length`, missing `Host` on HTTP/1.1, blocked path syntax, empty or oversized flag |
| 404 | Unknown path, unknown or hidden challenge or writeup, and every blocked static path (traversal, dotfiles, symlinks escaping the root, directories). A blocked path is never confirmed to exist. |
| 405 | Path exists but the method is not allowed (with an `Allow` header) |
| 408 | A partially received request stalled past its deadline (a silent idle connection is closed without a response) |
| 413 | Declared body larger than the limit |
| 414 | Request target too long |
| 429 | Too many flag attempts on one challenge (with `Retry-After: 60`) |
| 431 | Header too long, too many headers, or total header bytes over the limit |
| 500 | Internal failure (for example an allocation failure under the memory limit) |
| 501 | Unknown method, or `Transfer-Encoding` (chunked bodies are not supported) |
| 503 | The database is busy or unavailable |
| 505 | HTTP version other than 1.0 or 1.1 |

## 4. How the main defenses work

### 4.1 Parsing and request smuggling

- **Incremental, line-based parser.** It only consumes complete lines, and the caller's buffer holds any partial data, so the same parser is safe under any delivery pattern (one byte at a time, or many requests at once).
- **Strict line endings.** Only CRLF terminates a line. A bare LF never completes a line, so the request is cut off by the deadline.
- **Header names must be HTTP token characters.** Control characters (including NUL, which would make string comparisons disagree with other components) and whitespace are rejected. A leading-whitespace line (obsolete line folding) is therefore rejected too.
- **Control characters and DEL are rejected in header values** (horizontal tab is allowed).
- **`Content-Length` is parsed digit by digit** with the limit checked inside the loop, so it cannot overflow, and a value that is empty, negative, or contains anything but digits is rejected.
- **Conflicting duplicate `Content-Length` headers** are rejected. Identical duplicates are accepted.
- **`Transfer-Encoding` is rejected with 501**, which also covers the `Content-Length` plus `Transfer-Encoding` smuggling shape.
- **HTTP/1.1 requests must include `Host`.**
- **Request target rules.** It must start with `/` (so absolute-form targets and `*` are refused), and control characters anywhere in it are rejected. The query string is split off at the first `?` and kept separate from the path. Neither is percent-decoded by the parser.
- **Pipelining is safe.** Bytes after a completed request stay in the connection buffer and are parsed as the next request. After any parse error the connection is closed, because the stream position can no longer be trusted.

### 4.2 Static files and path traversal

The handler applies these steps, in this order, for every request:

1. Only `GET` and `HEAD` are accepted.
2. **Percent-decode first**, rejecting malformed escapes and encoded NUL (`%00`). Decoding before checking means encoded `..` sequences are seen as what they are.
3. **Reject any path containing `/.`**, which blocks `..` segments and every dotfile (`.git`, `.env`, `.htaccess`, ...) before the filesystem is touched.
4. Append `index.html` to paths ending in `/`.
5. Resolve with `realpath()` and require the result to be inside the **resolved** document root. The comparison checks for `/` or end-of-string after the root prefix, so a sibling directory such as `public-secret` cannot pass as `public`. Because `realpath()` resolves symlinks, a link that points outside the root is rejected.
6. `open()` the file and call `fstat()` **on the open descriptor** (no check-then-use race), and require a regular file.
7. Enforce the 8 MiB size cap.
8. Every rejection is a plain **404**, so the server never confirms whether a protected path exists.

**Challenge attachments** live in `public/files/<challenge>/` and are served by this same handler. Unknown extensions are sent as `application/octet-stream`, so browsers download them instead of rendering them, and `nosniff` prevents type guessing. The server never executes an attachment. Treat every attachment (for example the compiled `checker`) as untrusted when you open it yourself, and do not run attachments on a machine you care about unless you built them.

### 4.3 Response hardening

Every response, including error pages, carries:

| Header | Value / purpose |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `Content-Security-Policy` | `default-src 'self'` plus `img-src 'self' data:`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `no-referrer` |
| `Permissions-Policy` | camera, microphone and geolocation disabled |

A handler may set its own value for any of these, and the default is only added when the header is absent. API responses also carry `Cache-Control: no-store`.

**The CSP is a rule for the frontend.** There must be no inline `<script>`, inline event handlers (`onclick="..."`), `<style>` blocks or `style="..."` attributes. JavaScript and CSS live in separate files under `public/`, and event handlers are attached with `addEventListener`.

`Content-Length`, `Connection`, `Date` and `Server` are generated by the serializer, and handlers cannot override them. This prevents a handler bug from producing a response with wrong framing.

HSTS is deliberately not sent yet. It will be added once the site has its own domain and TLS.

### 4.4 Logging

- **Two streams:** access lines on stdout, diagnostics on stderr, so they can be redirected separately.
- **One `write()` per line.** Lines from different child processes never interleave.
- **The logger replaces control characters** in every message and saves and restores `errno`, so logging never disturbs error handling.
- **Access-log fields are cleaned:** quotes, backslashes and control characters become `_`, and long values are truncated, so a crafted path or `User-Agent` cannot break the format or forge a line.
- **Never logged:** request bodies (so never a submitted flag), `Cookie`, `Authorization`, `Referer`.
- **Client address:** the peer address, or `CF-Connecting-IP` only when `trust_proxy` is on, the peer is loopback **and** the value is a valid IPv4 or IPv6 address. Otherwise a forged header cannot change the logged address.
- **Privacy:** access logs contain client IP addresses and the full request target including the query string. Keep them private and rotate or delete them accordingly. Do not put secrets in query strings.

### 4.5 Resource exhaustion

- **Connection cap.** At `max_children` the parent stops accepting. New clients wait in the kernel backlog, and the server does not fork without bound. The parent wakes on `SIGCHLD` (using `sigsuspend` with the signals blocked around the check, so there is no lost-wakeup race) and on shutdown signals.
- **Deadlines instead of `alarm()`.** Each connection has an absolute deadline: a short idle deadline while waiting for a request, then a request deadline once the first byte arrives. Each `read` and `write` sets its socket timeout to the time remaining. A client that sends one byte at a time is cut off at the request deadline regardless of how slowly it sends. The same mechanism works in the serial model, where a process-wide `alarm()` would kill the server.
- **Per-child limits** (address space, CPU time, file descriptors) bound the damage one connection can do. An allocation failure under the memory limit becomes a 500 response, and the child survives.
- **Predictable memory per request:** the request object is a fixed size (about 31 KB) and a body buffer is allocated only after its declared size passes the limit. List endpoints are capped (200 challenges, 50 writeups per page), and the largest single response is a writeup of at most 256 KiB.

### 4.6 Process lifecycle

- **Signal handlers only set a flag.** No logging or other non-async-signal-safe work happens inside a handler.
- **Graceful shutdown.** On `SIGINT` or `SIGTERM` the parent stops accepting, signals its children, and waits for the grace period. Idle keep-alive children leave promptly, and in-flight responses complete and are sent with `Connection: close`. Anything still running after the grace period receives `SIGKILL`.
- **Children are tracked in a PID table**, so shutdown signals reach exactly the server's own children and not the whole process group.
- **Zombie reaping** happens in the `SIGCHLD` handler. Children that die from a signal are recorded and reported by the parent.
- **Descriptor hygiene.** The parent closes each client socket right after `fork()`, the child closes the listener, and accepted sockets use `SOCK_CLOEXEC`.

### 4.7 Data layer

- **Prepared statements only.** Every value is bound as a parameter. No SQL text is ever built from input. Slugs are validated against `[a-z0-9-]` before they reach a model, and the schema repeats the rule in a `CHECK`, so even code that bypasses validation cannot store an unsafe slug.
- **Schema as a second layer of validation.** `STRICT` tables, `CHECK` constraints on lengths (in bytes), ranges and enumerations, foreign keys on, and `trusted_schema` off.
- **No connection crosses a `fork()`.** The migration connection is closed before the server forks, and a `pthread_atfork` handler clears the thread-local connection pointer in children.
- **Migrations are transactional** (one transaction per file, including the version bump), and an older server refuses to start on a newer database.
- **File permissions.** The database directory is created `0700` and the file `0600`. The write-ahead log and shared-memory files follow the same umask. The database holds salted hashes, not flags, but it still should not be readable by other users.
- **Backups** contain the same data as the database and need the same protection.

### 4.8 Flags and the submission endpoint

- **Storage.** For each challenge, `flag_salt` is 16 random bytes (OpenSSL `RAND_bytes`) and `flag_hash` is `SHA-256(flag_salt || flag)`. The plaintext flag exists only in `tourneyctl`'s memory (wiped with `explicit_bzero` afterwards) and in the seed script.
- **Why salted SHA-256 is enough here.** Flags are long random strings, so offline guessing is hopeless even with a fast hash. The salt means identical flags on two challenges produce different hashes, and precomputed tables do not work. Human-chosen passwords are different: they will use PBKDF2 when accounts exist.
- **Verification.** The server recomputes the hash with the stored salt and compares with `CRYPTO_memcmp`, so timing does not reveal how many bytes matched.
- **Input handling.** The flag is the plain-text request body: 1 to 256 bytes, no NUL byte, surrounding whitespace trimmed (so `echo flag | curl -d @-` works). It is never echoed, logged or stored. Only `(challenge, correct, time)` is recorded.
- **Rate limit.** A submission is refused with `429` when the challenge already has 30 attempts in the last 60 seconds. The count comes from the `submissions` table, so it is shared by all children and survives restarts.
- **A wrong flag is a normal `200`** with `{"correct":false}`. Only malformed requests and abuse get error statuses.
- **Hidden challenges** (`published = 0`) answer exactly like missing ones: `404`.

### 4.9 Content authoring (`tourneyctl`)

- **Flags never appear on the command line.** They are read from a file or standard input (arguments would end up in shell history and `ps` output), limited to one line of 1 to 256 characters, and the buffer is wiped after use.
- **Validation before the database:** slug format, field sizes in bytes, UTF-8 validity, no NUL bytes, and `--source-url` restricted to `http://` and `https://` addresses without whitespace (so a `javascript:` URL can never be stored).
- **Destructive commands need `--yes`.** Deleting a challenge also deletes its submissions.
- **It has no network surface.** It is a local program that opens the same database file, so it must run as the same user as the server.
- **The seed script contains every solution** and is for development only. Do not publish the real flags of a live competition in a public repository.

### 4.10 Frontend

- **No HTML-string sinks.** The JavaScript never uses `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write`, and the frontend test fails if one appears. Elements are built with DOM calls and server text is set through `textContent`.
- **Inline code is forbidden twice:** by the server's CSP at runtime, and by a lint in the frontend test before the browser ever sees it.
- **Links built from data are validated.** Attachment links must match `/files/<slug>/<file>` with a restricted character set. External links must parse as `http:` or `https:`, and open with `rel="noopener noreferrer"`.
- **Query parameters are validated** against the slug pattern before they are used in an API path.
- **Browser storage.** The only stored value is the list of solved slugs in `localStorage`, wrapped in `try/catch`. It is a convenience, not a record, and nothing trusts it.

## 5. Verification

All suites below pass at `v1.0`. Record the commit they were last run against in [Testing.md](Testing.md).

### 5.1 Unit tests (`make test`)

Parser, response builder, router, configuration loader, logger, JSON writer, URL and query helpers, UTF-8 and slug helpers, hashing, the database layer and both models. Built with `-Wall -Wextra` and run under AddressSanitizer and UndefinedBehaviorSanitizer with `make test SAN=1`. The database tests include the fork-safety test (a child gets its own working connection while the parent's keeps working), constraint tests, an injection-attempt test, and a migration test that checks a failing migration leaves no partial schema.

### 5.2 Attack suite (`tests/integration/test_attacks.sh`)

Raw-socket requests (so no client normalizes or rejects them first) against a server started with an isolated document root:

| Category | Cases |
|---|---|
| Malformed requests | garbage request line, unknown method, HTTP/2.0, missing `Host` on 1.1 (and the allowed 1.0 case), absolute-form target, `OPTIONS *`, tab in path, 2000-character path, 5000 bytes with no CRLF |
| Header abuse | NUL in a header name, space in a header name, DEL in a value, 600-byte value, 5000-byte line, 60 headers, total header bytes over 16 KiB |
| Bodies and framing | conflicting `Content-Length`, non-numeric, negative, 2 MB, overflow-sized, chunked, `Content-Length` plus `Transfer-Encoding`, small body consumed, pipelined requests, close after a parse error |
| Path traversal | `/../../../etc/passwd`, encoded dots, encoded slashes and backslashes, `//etc/passwd`, `/./../`, a dotfile, a symlink to `/etc/passwd`, `%00` truncation. Each must return 400 or 404 and never any outside content. |
| Response hygiene | security headers present on error responses, no header injection through an encoded CRLF in the path |
| Log hygiene | no forged log line through an encoded newline, quotes in `User-Agent` neutralized, forwarded IP ignored with `trust_proxy` off, and with it on a valid address is used while invalid values (`999.1.1.1`, `<script>`) are ignored |

### 5.3 Limits suite (`tests/integration/test_limits.sh`)

Runs with short timeouts so it finishes in about a minute:

| Category | Cases |
|---|---|
| Connection cap | 14 idle connections against a cap of 8: children never exceed the cap, a queued client is served once idle children expire, the server survives |
| Timeouts | an idle connection closes silently with no response and no access-log line; a half-sent request gets 408 within its deadline; a slowloris client is cut off with 408 long before it finishes |
| Keep-alive rules | the connection closes after `max_requests_per_conn`, the last response announces `Connection: close`, a routed 404 keeps the connection open |
| Leaks | the parent's descriptor count is unchanged after 300 requests and there are no zombie children |
| Crash reporting | a child killed by a signal is reported in the error log and the server keeps running |
| Shutdown | clean exit with idle connections open, shutdown is not delayed by idle connections, an immediate restart binds the port, an in-flight 6 MB download completes during shutdown, stragglers are killed after the grace period and logged |

### 5.4 API suite (`tests/integration/test_api.sh`)

Runs against a fresh database seeded through `tourneyctl`:

| Category | Cases |
|---|---|
| Disclosure | no list or detail response contains a hash, a salt or a flag; hidden challenges and writeups are absent from lists and answer `404` |
| Input handling | unknown, malformed and injection-shaped slugs return `404`; empty, oversized (300 bytes) and NUL-containing flags return `400`; a trailing newline is trimmed |
| Behavior | correct and wrong flags return the right JSON; `GET` on the submit path is `404`; `DELETE` on a list route is `405` with `Allow`; `HEAD` works |
| Logging | a submitted flag (marked with a unique needle) never appears in the access log |
| Rate limit | the 31st attempt in a minute returns `429` with `Retry-After`, even for the correct flag |
| Concurrency | 100 submissions from 20 parallel clients produce no `5xx` (SQLite writer contention is absorbed by the busy timeout) |
| Writeups | newest first, pagination, `limit` clamped to 50, bad `limit` and negative `offset` handled, quotes, backslashes and non-ASCII text round-trip correctly |
| Server health | no `ERROR` lines in the server log after the suite |

### 5.5 Frontend suite (`tests/integration/test_frontend.sh`)

A static lint (no inline styles, event handlers or scripts; no HTML-string sinks in the JS; every referenced file exists) plus checks that each page is served with the right content type and a CSP header. A manual browser checklist (console clean under the CSP, a challenge titled `<img src=x onerror=alert(1)>` renders as text, keyboard navigation, dark mode) is in [Testing.md](Testing.md).

### 5.6 Fuzzing (`make fuzz`)

- **Target:** `http_parse`, through `tests/fuzz/fuzz_parser.c`.
- **Properties checked on every input:**
  1. no memory or undefined-behavior errors (ASan and UBSan, with `-fno-sanitize-recover=undefined`);
  2. **split-invariance:** parsing the bytes in one call gives exactly the same result as feeding them in small pieces, the way the connection handler does;
  3. **structural invariants:** strings terminated and within bounds, no control characters in the parsed path, query or headers, a completed request is fully formed, and every error status is one the server knows how to answer.
- **Corpus:** ten seed requests (plain, with query, with body, pipelined, duplicate `Content-Length`, chunked, malformed) plus a token dictionary for the coverage-guided runner.
- **Result:** 2,000,000 mutated inputs (seed `1792269555`), **no crashes and no failed checks**.
- **Limits of this result:** the gcc driver is a mutation fuzzer and is not coverage-guided. A longer coverage-guided run (`make fuzz-clang`) is recommended before relying on the parser against hostile traffic for a long time. Only the parser is fuzzed so far.

### 5.7 Deployment test

The server was run behind a Cloudflare quick tunnel on Ubuntu, and was reached from outside the home network with no errors. With `trust_proxy` on, the access log recorded real client addresses.

### 5.8 Performance baseline

Behavior under normal load and at saturation (200 connections against a cap of 64) is recorded in [Benchmarks.md](Benchmarks.md), to compare against the later models.

### 5.9 Reproducing everything

```bash
make clean && make test SAN=1        # unit tests under sanitizers, then every integration suite
make fuzz ITER=2000000               # gcc mutation fuzzer (replay a crash: ./build/fuzz_driver fuzz-crash.bin)
make fuzz-clang SECS=600             # optional: coverage-guided run (needs clang)
```

Run attack scripts, fuzzers and load tests against `127.0.0.1` only, never through a public tunnel URL.

## 6. Known limitations

These are deliberate omissions or accepted trade-offs, not forgotten items.

| Limitation | Notes |
|---|---|
| No TLS | Cloudflare terminates TLS for tunnel deployments (flags are encrypted up to Cloudflare, and the provider can see them). Own TLS is planned. Over plain HTTP, flags are visible to anyone on the network path. |
| The submission rate limit is global per challenge | It stops brute-forcing, but anyone can also lock a challenge for a minute by sending wrong flags. Fixing it needs identity (accounts or reliable per-client limits), which comes later. |
| No accounts | Submissions are anonymous. "Solved" marks exist only in the browser's `localStorage`, and the platform keeps no scoreboard. |
| Anyone can read all published content | Hidden items are unpublished with `tourneyctl hide`. Nothing in `public/` can be private. |
| `public/files/` is world-readable | Never put anything private there. The seed script regenerates it. |
| Attachments are untrusted artifacts | The server never executes them. Do not run them carelessly yourself. |
| Chunked request bodies unsupported | Answered with 501. |
| Static files are read fully into memory | 8 MiB cap per file. Streaming comes with the event-loop version. |
| No per-IP connection or rate limits | Under fork, counters in memory are not shared between children. The tunnel provides this protection today. |
| At the connection cap, new clients wait in the kernel backlog | They are not told "503". Long waits are visible in the saturation benchmark. |
| The response write budget is the whole `request_timeout_sec` | A slow but legitimate client downloading a large file can be cut off. A per-progress write timeout is the better design and a planned improvement. |
| All dotfiles are hidden | This includes `/.well-known/`, which will need an explicit exception if certificate validation or similar ever requires it. |
| Request body is allocated when the headers finish | Bounded by the body limit and the child cap here. It must become incremental in the epoll version, where one process holds thousands of connections. |
| A database connection is opened per forked child on first use | Costs time per connection under fork. Keep-alive amortizes it. |
| Writeups are shown as preformatted text | There is no Markdown rendering, which also means there is no rendering attack surface. A renderer must build DOM nodes, never HTML strings. |
| Only one event (`practice`) is reachable through the API | The schema supports many events. Adding event selection is a small change (see [Schema.md](Schema.md)). |
| No HTTP/2, no compression | |
| Logs are not rotated | Redirect to a file and rotate externally. |
| Configuration values cannot contain `#` | Everything after it is treated as a comment. |
| Quick tunnel URLs are temporary | A stable address needs a named tunnel and a domain. |
| Only the parser is fuzzed | The URL decoder, query parser, JSON writer, header-token helper and configuration loader are good next targets. |

## 7. Operational checklist

Before exposing the server:

- [ ] Release build (not the sanitizer build): `make clean && make`
- [ ] `bind_addr = 127.0.0.1`, and `trust_proxy = on` only when running behind `cloudflared`
- [ ] Running as a normal user, never root
- [ ] The document root contains only files meant to be public (no backups such as `*~`, `*.bak`, `*.swp`; no symlinks; no test files). `public/files/` contains only generated attachments.
- [ ] The database lives outside `public/`, the data directory is `0700` and the file `0600`
- [ ] The database was seeded with the real challenges, not the development seed. The seed script's flags are not used on a live site.
- [ ] No demo or lab routes are registered
- [ ] Hidden challenges and writeups are really unpublished (`tourneyctl challenge list` shows `pub`)
- [ ] Backups are taken with the online `.backup` command and stored with the same protection as the database
- [ ] Logs are private, and the error log is read after every public session
- [ ] `make test SAN=1` is green on the exact commit being deployed

## 8. Planned security work

| Phase | Item |
|---|---|
| Accounts | Password hashing with PBKDF2 from OpenSSL (no hand-written crypto); random session identifiers; cookies with `HttpOnly`, `Secure` and `SameSite`; CSRF protection on state-changing requests; per-user rate limits and a one-solve-per-user rule enforced by the schema |
| Events | Visibility and submission windows enforced inside the SQL (`starts_at`, `ends_at`), so no handler can forget the rule |
| Lab endpoints | Registered only when explicitly enabled, never in a deployment |
| TLS | OpenSSL inside `net/conn.c` only; blocking TLS on the fork version first, then non-blocking TLS in the epoll loop; HSTS once a domain exists; no `sendfile` |
| epoll version | Incremental body buffers, timer-based deadlines, bounded per-connection memory, and a worker pool for blocking database calls |
| Hardening | Per-progress write timeouts, a JSON `404` for unknown `/api/` paths, an optional Markdown renderer built on DOM nodes |
| Testing | Fuzz the URL decoder, query parser, JSON writer and configuration loader; run the coverage-guided fuzzer for longer; add a TLS handshake test suite |
